> 2026-11-19 整理。命名按时间顺序：**方案1 = 项目原有的分步标准流程**
> （demo1→demo2 两个独立脚本先后跑）；**方案2 = 今天新建的官方一键管线**
> （按 slam_toolbox + Nav2 官方架构串成一条命令）。本文档说明两者架构区别、
> 实测数据，以及共有的"原地转圈"问题的根因。

## 一、两个方案是什么（时间线：方案1 先存在，方案2 今天新增）

| | 方案1：分步标准流程（原有） | 方案2：官方一键链路（2026-11-19 新增） |
|---|---|---|

## 二、架构差异（核心区别）

| 维度 | 方案1 分步流程（原有） | 方案2 官方一键链路（新增） |
|---|---|---|
| **Gazebo 生命周期** | demo1 结束时杀掉全部进程（含 Gazebo），demo2 重新起仿真、车回到出生点 | **全程不重启**。机器人探索结束的位置直接开始巡逻，世界连续 |
| **定位源切换** | 各自独立：demo1 只用 SLAM，demo2 只用 AMCL，中间隔一次完整重启 | 同一会话内无缝交接：slam_toolbox 提供 map→odom → 停 SLAM → AMCL 接管。**两个定位源绝不同时运行** |
| **存图时机** | demo1 末尾存图 → 部署 `obstacle_field.*` → demo2 启动时 `cp -u` 到 `~/car_maps/` | SLAM 存活期间用 `map_saver_cli` 存图（官方要求：停 SLAM 前存） |
| **初始位姿** | 用固定出生点坐标 (-4.5, -4.5)，车恰好在出生点所以成立 | 自动计算：`slam map→odom` TF ⊕ `/odom` 当前里程计位姿（探索结束时车已不在出生点） |
| **覆盖率参考图** | 用部署的 `obstacle_field.pgm`（实测曾被 SLAM 残图覆盖污染，导致 demo2 卡死） | `gen_gt_map.py` 现场重新生成 GT 图（与世界几何完全一致，**不怕被覆盖污染**） |
| **地图产物** | 直接写 `obstacle_field.*`（demo2/3/4 靠同名约定消费） | `~/car_maps/official_map.{pgm,yaml}`（独立命名，不污染 demo2/3/4 的消费图） |
| **中断恢复** | 同样有续跑，但分两段，段间失败需人工重跑 | 一个脚本内自动续跑（8 次），全程无人值守 |
| **可视化** | 两个会话，中间有清场黑屏（观感"割裂"） | 全程一个桌面会话，从建图看到巡逻结束 |
| **出问题的隔离性** | demo1 失败可单独重跑，demo2 不受影响 | 阶段A失败 → 整条管线终止 |

## 四、"原地转圈"问题：**两方案共有的弱点**

### 现象
机器人在场地中反复原地旋转或绕圈，覆盖率长时间不动（地图 md5 不变），
脚本不断打印"地图连续 120 秒未更新 → 触发停滞续跑"。

### 根因（按出现概率排序）
1. **roadmap_explorer frontier 候选不可达**：剩余未知区多被障碍物围成
   小封闭区，探索器反复把 Nav2 目标发给不可达前沿 → DWB 局部规划器
   原地旋转试探 → 超时 → "no achievable frontiers" → 续跑后再次选到
   同一批前沿，形成循环。两个方案的探索器、续跑逻辑**完全相同**
   （方案2 的循环代码就是从方案1 的 `run_demo1_roadmap.sh` 移植的），
   所以转圈**不是新架构引入的**，是 roadmap_explorer 在本场景的固有行为。
2. **Nav2 时间戳竞态**：续跑连续发目标时，"The timestamp of the received
   goal is older than the current goal. Ignoring"导致目标被丢弃（此前实测确认过）。
3. **DWB 狭窄区震荡**：DWB 在两障碍夹缝中左右摆动出不来。

### 实测对比
| 运行 | 表现 |
|---|---|
| 方案1 demo1（历史） | 两次卡住（49.98%、92.75%），靠续跑恢复到 96.49% |
| 方案2 第1轮 | 31% 平台期约 5 分钟 → 恢复 → 96.11% |
| 方案2 第2轮（演示） | 33% 卡 15 分钟（续跑 7 次）→ 爬升至 38.7%+，恢复慢 |

### 可能的缓解手段（尚未实施）
- 停滞超过 N 次续跑后，把机器人"瞬移"回场地中心再续跑（绕开不可达前沿包围圈）；
- DWB 换 RPP 控制器（rosnav 项目默认），旋转震荡更少；
- 探索器参数：加大 frontier 搜索半径、降低重复目标权重；
- 对答辩场景：提前用方案1 跑好 96.49% 图，现场只跑方案2 的阶段B（定位+巡逻），
  探索环节放录屏。

## 五、功能完整度与选择建议

### 功能完整度
- **方案1（分步）功能完整**：demo1 探索建图 / demo2 航点巡逻 / demo3 GMR-RRT*
  算法演示（论文核心）/ demo4 自然语言+相机，四个演示全部建好且跑通过。
  它唯一缺的是"自动串联"——demo 之间要人工切换脚本。
- **方案2（一键）目前只覆盖 demo1→demo2**（探索建图→存图→切定位→巡逻），
  demo3/4 尚未串入。**不完整的是方案2**，方案1 是功能全但流程断。

### 选择建议

| 场景 | 建议 |
|---|---|
| **现场一键演示**（连贯观感最重要） | 方案2，但要接受探索随机性：可在 RViz 旁开终端 `tail -f /tmp/official_demo.log`，卡住时向观众讲解续跑机制（本身是亮点） |
| **稳妥出数据/录视频** | 方案1（demo1 单独跑到 95%+ 存图，确认后再跑 demo2） |
| **混合（推荐给答辩）** | 提前用方案1 建好 96.49% 图 → 现场只跑方案2 阶段B：`ros2 launch car_nav localization_nav.launch.py map:=~/car_maps/official_map.yaml run_mission:=true`，跳过探索的随机性 |
